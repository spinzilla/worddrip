## 目标（一两句话，用户能看懂）

## 要做成什么样

1. **晋级规则**（`next_state`）：
   - L1→L2→L3→L4 不变（2 / 4 / 8 / 16 天）。
   - L4 答对 → **L5**，45 天后到期；L5 答对 → **L6**，90 天；L6 答对 → **L7**，180 天；L7 答对 →「✅已掌握」（不再复习）。
   - L1–L4 答错 → L1（不变）；**L5–L7 答错 → L3**，8 天后到期。
   - 首考（🌱待考察）：看过释义 → L1（不变）；答错 → L1（不变）；**不看释义直接答对 → L3**，8 天后到期（原来是直接已掌握）。
   - 同日复检、选择题不改等级（现有规则不变）。
2. **数据库迁移**（`SCHEMA_VERSION` 加 1）：已有「✅已掌握」的词改成 L5，到期日 = 迁移当天 + 7 + （按词条 id 算的稳定哈希 % 60）天，在 7–66 天里摊开；在词条备注里追加一句「{日期} 已掌握转入保温复习」。🧊冷库、🌱待考察不动。迁移只跑一次（靠版本号），重复启动不再动。
   - **注意（统筹 2026-11-20 补）**：`review_word.level` 有 `CHECK (level IS NULL OR level BETWEEN 1 AND 4)`（schema.rs 约 48 行），要放进 5–7 必须重建这张表。SQLite 不能直接改 CHECK，而且 `vocab_example`、笔记等表对 `review_word` 有 `ON DELETE CASCADE` 外键——**直接 DROP 旧表会把例句、笔记全部级联删掉**（021 出过同类事故）。必须按 SQLite 官方「12 步改表」做：事务里 `PRAGMA foreign_keys=OFF` → 建新表（CHECK 改成 1–7，其他列、默认值、索引、触发器原样）→ 拷数据 → 删旧表 → 新表改名 → 重建索引 → `PRAGMA foreign_key_check` 无输出 → 提交后 `PRAGMA foreign_keys=ON`。单测要证明：迁移前后例句、笔记、复习日志等关联表行数一样。
   - 同步：服务器按行原样存，不用改；但**还没升级的旧版应用**收到 level=5 的行会被本地 CHECK 拒绝。结束报告里写清楚旧版收到这种行时会怎样（报错、跳过还是整次同步失败），统筹好提醒用户两台设备一起升级。
3. **全部认状态的地方都认 L5–L7**：到期队列、出题（L5–L7 照 L4 出题）、闪卡、浏览筛选、状态说明、最早到期日、Markdown 导出和导入（`parse.ts` 等能读回 L5–L7）、同步（状态是普通文本列的话确认不用改；有白名单就补上）。
4. **界面文案**：L5–L7 显示成「保温 1 / 保温 2 / 保温 3」（英文 Long-term 1/2/3），后面照旧带到期日；浏览页「复习中 L1–L4」筛选改成「复习中」并包含 L5–L7，另加一个「保温中」筛选。词条页状态旁加一句小字说明：「已过 L4，隔 45/90/180 天再各考一次，都对才算掌握」。
5. 写作练习挑建议用词（`app/utils/writing/wordPicker.ts`）原来排除「已掌握」，保温中的词照常可以被挑。
