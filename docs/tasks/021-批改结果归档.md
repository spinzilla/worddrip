## 目标（一两句话，用户能看懂）

批改完点「归档」，先看要写入什么，确认后才写：这篇作文和批改结果存下来，错误进错误档案，高频错误的计数和状态自动更新。下一次批改就能认出你的老毛病。

## 从哪看起

- 规则：`docs/coach-rules/skills/english-learning/SKILL.md` 的 A.5「归档流程」、A.9.1 状态流转，以及「通用铁律」第 1、2 条。
- 数据表来自 018（高频统计、批次、错误项），查询和页面在 019，批改结果的结构在 020。
- 写入事务照 `app/src-tauri/src/vocab/import.rs` 的写法。
- 坑：
  - **归档只追加不覆盖**（铁律 1）：旧批次和旧错误项一个字都不能改。只有高频 Top 的计数、最近一次和状态允许更新。
  - **写完必须告诉用户改了哪几处**（铁律 2）。
  - 新错误归到 Top 的哪一类由模型建议，用户在预览里可以改；没有对应类别时新增一行。
  - 同一次批改重复点「归档」不能写两份。
  - 状态流转：🔴 反复犯 → 🟡 已改善（连续 3 次未犯）→ 🟢 已掌握，规则写在 A.5 和 A.9.1，两处说法不完全一样，**以 A.9.1 为准**，并在结束报告里写明。

### 问题清单（按严重程度）

1. **中｜重新导入错误档案会静默删掉已归档的作文和连续未犯计数。** `coach_essay.batch_id` 和 `coach_top_progress.top_id` 都是 `ON DELETE CASCADE`，而 `errors::insert_rows` 每次导入都执行 `DELETE FROM error_item; DELETE FROM error_top; DELETE FROM error_batch;`（`errors.rs:90-96`），`schema::open` 打开了 `foreign_keys=ON`。复现：先在应用里归档一篇作文 → 再到「词库 → 导入」重新导入同一份错误档案 Markdown → `coach_essay` 和 `coach_top_progress` 变空，归档的作文原文/批改 JSON/连续未犯计数不可恢复（已用 SQLite 按同样 DDL 和删除顺序验证：两张表都变 0）。本卡三条验收标准不覆盖这条路径，但会真实丢数据；建议下一张卡把外键改成不级联（或导入前提示/禁止覆盖），本卡先记录。
2. **低｜版本升到 5 后，只读浏览可能先报「版本不兼容」。** `query::coach_at` 要求 `user_version == SCHEMA_VERSION` 且只读打开，只有 `schema::open` 才会迁移；用户升级应用后直接打开教练页（`vocab_coach_browse`）会看到「词库数据库版本 4 与本应用支持的版本 5 不兼容，已停止读取」，直到走一次归档/导入/复习等写路径才自愈。022 的验收记录已记过同类问题（018 起存在），不是本卡引入，但本卡把版本从 4 推到 5 会让现有用户首次遇到。复现：造一个 `user_version=4` 的库 → 调 `vocab_coach_browse` → 报不兼容；调一次 `vocab_coach_archive_preview` 后再查 → 正常。
3. **低｜无关的 UTF-8 BOM。** 上面列的 7 个源文件（含 `lib.rs`、`schema.rs`、两个 TSX、`api.ts` 等）第一行多了 `EF BB BF`，本卡文件标题行也多了 BOM；`cargo test`、`tsc` 均通过，但和仓库其他文件不一致，建议提交前去掉。
4. **低｜前端预览逻辑是测试专用副本。** `buildArchivePreview`、`missedStatus`、三个状态常量在 `archiveWrite.ts` 里复制了一份 Rust 规则，应用运行时并不调用；`test-coach-archive-write.mjs` 的“实际写入”只是 JS 模拟。规则若只改 Rust，脚本仍会绿。真实一致性目前靠 Rust 用例保证。
5. **低｜`error_top.count` 不是纯整数时整次归档会被拒绝。** 错误档案导入按原样保存该列（`errors.ts` 取表格单元格），`archive.rs` / `archiveWrite.ts` 用 `Number`/`i64` 解析；只要有一行写成「多」「3 次」之类，预览和归档都会报「高频错误次数必须是非负整数」，而且没有跳过单行的选项。现有 fixture 里被跳过的六列坏行不会入库，但五列的非数字行会。复现：导入一行 `| 1 | 主谓一致 | 多 | 2026-01-02 | 🔴 在犯 |` → 打开归档预览 → 报错，无法归档。
6. **低｜连续快速改类别时预览可能显示旧结果。** `changeArchiveKind` 每次触发一个异步预览请求，没有取消/序号保护；后发先至时页面显示的是较早选择的预览。确认写入仍按最新的 `archiveItems` 提交、后端会重新 `plan()`，所以落库不会错，但“预览与实际写入一致”在这个竞态下只是最终结果一致，显示的预览可能对不上。复现：两秒内连续改两个下拉框，观察预览闪回。
