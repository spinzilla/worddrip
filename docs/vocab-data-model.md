# 词库数据模型与速查页调研

调研日期：2026-11-04。范围仅限任务卡 005 指定的本地文件；外部来源均只读，没有运行生成器，也没有连接服务器。

## 结论先读

- 三个 Markdown 不是同一种表：学术升级库是「5 列升级对照 + 6 条自查」，复习库是「6 列总词表」，错误档案是「统计表 + 多批自由格式明细 + 清单」。导入时应分开建模。
- 当前主库有 **78 条表格记录**，另有 **6 条写作自查**；总词库有 **486 行**，但只有 **480 个不区分大小写的不同词目**，所以不能用单词文本当唯一主键。
- 生成器的解析规则可以抽出来复用，但不能直接 `import build_vocab_page.py`：文件顶层会读文件并覆盖写 HTML。应另做纯解析/JSON 导出层，并补异常报告。
- 页面是「构建时嵌入本地数据 + 运行时服务器评论/AI」。每日推荐、到期筛选、闪卡不需要服务器；批注楼、未读、置顶和 AI 回复需要服务器。
- 存储建议：**Hermes 词库以 Rust 侧 SQLite 为唯一事实源，优先复用现有 `rusqlite`**；现有 LinguaClip 的 IndexedDB 卡片和音频先不迁移。详见第 5 节，具体实现方式仍由架构负责人拍板。

### 1.1 `D:\Hermes\english\词汇\学术升级库.md`

#### 条目数与计数口径

- 「词汇升级」表格：**78 条**，只数 5 列数据行，不含表头、分隔线。
- 「写作自查对照」：**6 条**无序列表项。

#### 一条表格记录的字段

| Markdown 列 | 含义 | 生成器/页面字段 | 注意事项 |
|---|---|---|---|
| 日常/口语 | 用户卡壳时会搜的表达 | `f` | 也是普通升级词条的评论锚点 |
| 学术升级 | 首选及备选表达、搭配和警告的混合文本 | `b`，去掉 `**` 后由前端 `parseBack` 再拆 | 不是单纯的「答案词」 |

| 备注 | 期号、用法、纠错等 | 新词条用于拼 `s` | 老词条可能被硬编码摘要替代 |

页面另外补了三个不在 Markdown 表格里的字段：`t`（`w/p/m/c` 分类）、`k`（额外中文搜索词）、`s`（页面元信息）。它们来自 `INHERIT`、`NEW_TK`、`F_ALIAS`，不是原表的隐藏列。



### 1.4 导入时的最小数据约束

1. 每条导入记录保留稳定 `id`、来源文件、来源行号/区块、原始顺序和原始 Markdown；不要用词文本、`f` 或评论锚点代替主键。
2. 学术升级例句宜拆成「候选表达 + 例句 + 是否 AI 草稿」子记录，保留原 `⧉` 文本用于无损导出。
3. 复习词允许同词多行；`状态`、`到期日`、`备注中的历史`先原样保留。L1–L4 与 LinguaClip 的 FSRS 是两套调度，不应自动互相换算。
4. 错误档案采用「高频统计、批次、错误项、待巩固、作文索引」分表或分集合；自由元数据可先保留 JSON，同时保留原文。
5. ✏️笔记收件箱与 💬评论楼是两套数据，后续仍分开存；评论锚点另做「旧锚点 → 稳定词条 ID」映射。

## 2. 生成器怎么解析，能否复用

来源：`D:\Hermes\english\scripts\build_vocab_page.py`。本任务只静态阅读，没有执行。

### 2.1 主库解析

1. 找到精确以 `| 日常/口语` 开头的表头后进入表格，遇 `|---` 跳过，遇非 `|` 行结束。
2. 每行用 `s.strip("|").split("|")` 切列；至少 5 列才收，且只取前 5 列。
3. `学术升级`只去掉 `**`；例句按 `⧉` 分段，再用 `^(.+?):\s+(.+)$` 提取英文半角冒号后的句子，形成 `exw`。
4. `f` 精确命中 `INHERIT` / `F_ALIAS` / `NEW_TK` 时补 `t/k/s`；未命中则默认 `t="w"`、`k=""`、`s=出处`，并打印警告。
5. 额外追加硬编码 `SELF6` 六条自查，最后嵌入单文件 HTML。

前端 `parseBack` 继续把 `b` 拆成：首选/备选、括号注释、搭配、补充说明、警告。它只在中英文括号深度为 0 时识别分隔符；`/` 只有后面跟半角或全角空格才表示备选分界。

### 2.2 复习库解析

1. 正则截取 `## 总词库` 到下一个二级标题；按 `|` 切出 6 列。
2. 状态匹配 `^L\d` 的行进入 `DUE={w,lv,d}`；所有有效行进入 `WORDS={w,d,st,g}`，备注截到 160 字符，到期日非 `—` 时加 `du`。
3. 扫描 `词汇\2026MMDD.md`，兼容「编号 + 粗体词 + 词性 — 正文」「粗体词 — 正文」「英文词 — 正文」三类格式，按有无词性/例句和释义长度打分选较优释义。
4. EAGP 官方词表只作低优先级兜底，不覆盖期文件已有结果；最后用词目小写精确匹配 `PIDX`。

### 2.3 其他输入

- `daily-expressions\pool.json`：只取 `category === "sentence"`，经 `frames_groups.py` 分组，生成 `s#哈希` 锚点。
- `词汇\口语栏.md`：四列表格，映射为表达、释义、替换建议、期号。
- `GD\phase2.json`：读取 `sections`，用于 GD 分组展示。
- 最终把 `DATA/DUE/WORDS/SENTS/SPOKEN/GD` 全部作为 JSON 常量嵌入 HTML。

### 2.4 容易解析错或漂移的地方

| 风险 | 实际后果 |
|---|---|
| 所有 Markdown 表格都直接 `split("|")` | 单元格内未转义的 `|` 会错列；少于所需列会静默跳过，多于则截掉 |
| 主库表头、章节名和分隔符依赖精确格式 | 改标题、使用中文冒号、改 `⧉` 或括号风格都可能漏解析 |
| 例句键与前端拆出的候选词必须逐字一致 | 粗体/括号/斜线规范化不同会让例句挂不上 |
| `parse_ex_cell` 用对象存例句 | 同一条内候选键重复时，后值覆盖前值 |
| `t/k/s` 依赖 `f` 精确命中手工映射 | 改一个空格或标点就可能退回默认分类、丢搜索词；老条目 `s` 可能与 Markdown 备注漂移 |
| 自查同时存在于 Markdown 和 `SELF6` | 改一处不改另一处会导致页面与源文件不一致 |
| 前端只按特定规则拆 `/`、`；`、`：`、`⚠️` | ASCII 分号、无空格斜线、括号嵌套异常会改变候选数量或警告位置 |
| 复习备注和期文件释义会截断 | 页面不是无损数据；不能拿 HTML 反推完整原始库 |
| 期文件匹配只靠词目小写 | 「soak / immerse…」等组合行、变形词和别名可能匹配不到释义 |
| 脚本顶层直接读写 | 作为模块导入就会执行整个生成流程，不适合当纯解析库 |

### 2.5 复用结论

**可以复用规则和正则，不应原样导入脚本。** 后续最小改法是把解析函数抽成无副作用模块，再增加 JSON 导出命令；导入器应返回「记录 + 警告 + 错误 + 计数」，对缺列、缺映射、例句未挂载、重复词目给出报告。原始 Markdown 仍是导入来源，HTML 只用于核对，不作为回导数据源。

## 4. 服务器本地副本：接口与 JSON

只读来源：`D:\Hermes\vocab-notes\app\main.py` 和 `data\notes.json`。本地 `data` 目录只有 `notes.json`，**没有 `comments.json`、`state.json`、`ai_context.md`**，所以下述 comments 结构来自读写代码，不是对本地真实评论样本的观察。

### 4.1 鉴权

- `POST /api/auth` 校验访问码，成功种 `vocab_auth` Cookie：值是访问码对固定消息 `vocab-notes` 的 HMAC-SHA256，HttpOnly、SameSite=Lax、180 天。
- `GET /api/health` 和 `POST /api/auth` 不需要已有 Cookie；其余下列接口都由中间件校验 Cookie。
- 页面线上经 nginx 使用 `/vocab-api` 前缀，FastAPI 内部路由仍是下表的 `/api/...`。

### 4.2 接口清单

| 方法与路径 | 作用 | 鉴权 |
|---|---|---|
| GET `/api/health` | 健康检查，返回 `{"ok":true}` | 无 |
| POST `/api/auth` | 输入 `{code}`，校验并设置 Cookie | 无 |
| GET `/api/notes` | 返回全部 ✏️笔记收件箱 | Cookie |
| POST `/api/notes` | 输入 `{key,text}`，追加 `{date,text}`；key≤120、text≤500 字符 | Cookie |
| GET `/api/comments` | 返回 `{comments,pinned_off,unread}` | Cookie |
| POST `/api/comments` | 输入 `{anchor,text}` 追加用户评论；页面另发 `tag`；anchor≤200、text≤2000 | Cookie |
| POST `/api/comments/toggle` | 输入 `{anchor,id}`，切换软删除/恢复 | Cookie |
| POST `/api/pin` | 输入 `{anchor,off}`，取消或恢复评论提前 | Cookie |
| POST `/api/read` | 输入 `{anchor}`，记录该楼已读时间 | Cookie |
| POST `/api/ai-reply` | 输入 `{anchor,comment_id,entry}`，生成 AI 回复并追加到楼内 | Cookie |

### 4.3 `notes.json` 结构

本地真实内容是空对象 `{}`。按键到笔记数组的结构如下；示意不是本地真实记录：

```json
{
  "词条或归档键": [
    {"date": "YYYY-MM-DD", "text": "笔记正文"}
  ]
}
```

没有 id、deleted、author 字段；同一 key 只追加，服务器日期取当天。写入采用临时文件加 `os.replace`。

### 4.4 `comments.json` 结构

按代码推导为「锚点 -> 两级评论数组」；id 在该锚点内从 1 递增，用户与 AI 共用序号：

```json
{
  "be made up of": [
    {
      "id": 1,
      "author": "user",
      "text": "用户评论",
      "ts": 1760000000,
      "deleted": false,
      "reply_to": null,
      "tag": "note"
    },
    {
      "id": 2,
      "author": "ai",
      "text": "AI 回复",
      "ts": 1760000010,
      "deleted": false,
      "reply_to": 1
    }
  ]
}
```

其中 `ts` 是 Unix 秒；`reply_to` 仅 AI 回复指向用户评论 id；删除只改 `deleted`，数组项仍保留。`tag` 是当前页面会发送、台账要求支持的扩展值。

**本地副本存在版本差异：**当前生成器 `postComment` 发送 `tag`，台账也说后端有 `CommentIn.tag + VALID_TAGS`；但这份本地 `main.py` 的 `CommentIn` 只有 `anchor,text`，新增用户评论时也不保存 `tag`。按 Pydantic 默认行为，额外 `tag` 会被忽略。因此不能把本地副本当作「线上已经支持标签」的证据；线上版本未连接、未核实。

## 5. 存储方案建议：IndexedDB 还是 Rust + rusqlite

### 5.1 现有事实

- `app\utils\review.ts` 已有独立 IndexedDB `linguaclip_review`，存句子卡/单词卡及 FSRS 状态；`addWord` 能保存 `word/definition/example/ai` 和音视频来源。
- `app\mobile\store.ts` 已有安卓 WebView 可用的 IndexedDB `linguaclip_audio`，负责音频、缓存和恢复前副本，并请求持久化存储。
- `app\src-tauri\Cargo.toml` 已含 `rusqlite = { version = "0.37", features = ["bundled"] }`，本地词典已使用 SQLite，不代表还要新增一套原生依赖。
- 架构草案已经选择「双端同构 SQLite + 可导出 Markdown + 以后扩 FastAPI 同步」。本节的建议是与之对齐，并明确不要迁移现有精听存储。

### 5.2 对比

| 维度 | IndexedDB | Rust + rusqlite / SQLite |
|---|---|---|
| 安卓端 | 现有代码已跑在 WebView 数据层，接入快、不用写 Rust 命令；但数据受 WebView 生命周期和清理策略影响，备份要自行覆盖各 object store | bundled SQLite 可随 Tauri 安卓端使用，Windows/安卓同表同事务；要写迁移、命令层和安卓真机验证 |
| 导出回 Markdown | TS 直接序列化方便，但要自己保证排序、重复行、原格式和完整导出 | 同样要写序列化器；稳定 ID、来源行、顺序字段和事务更适合可靠往返，SQL 本身不会自动解决无损导出 |
| 以后服务器同步 | JSON 记录上传直观，但多对象存储、增量游标、冲突和删除标记都要另做 | 可按表做 `id/updated_at/deleted/revision` 增量同步和约束；应同步记录，不能直接两端复制同一个 SQLite 文件 |
| 阶段3「听错词入库」 | 可复用 `addWord`，近期改动最少；但 Hermes L1–L4 与 FSRS 卡容易形成两套事实源，需定义映射 | 新写入走 Tauri command，可保存来源视频、句子和词库 ID 的关联，统一查询/导出；短期需要桥接现有 IndexedDB 卡片 |
| 查询与约束 | 当前代码大量 `getAll` 后内存筛选，小库够用；复杂关联和唯一约束较弱 | 适合按状态/到期/来源查询、事务导入和重复行规则；需要防止过度建表 |
| 迁移成本 | 最低，复用现有工具函数 | 较高，但 rusqlite 已在依赖中；主要是 schema、迁移、命令和测试工作 |

### 5.3 推荐

**Hermes 学术升级库、复习库、错误档案、笔记和评论放 Rust 侧 SQLite，作为唯一事实源；优先复用现有 rusqlite。** React 通过一层很薄的 command/repository 访问，不在组件里散落 SQL。现有 LinguaClip 的 `linguaclip_review` 和 `linguaclip_audio` 暂留 IndexedDB，避免这张卡扩张成精听存储迁移。

阶段3只增加一个很薄的「听错词 → Hermes 待考察」写入入口，并保存来源引用；**不自动把 FSRS 状态换算成 L1–L4**。是否以后统一调度另开架构讨论。

无论选哪种技术，都必须先定稳定 ID、重复词目规则、评论锚点映射、追加/软删除策略、原始 Markdown 保留方式和同步冲突规则。直连 rusqlite 还是 Tauri 官方 SQL 插件属于后续实现拍板项，不应两种访问层混用。

### 5.4 拍板（Claude，2026-11-04）

采纳 5.3 的推荐，并定下实现方式：

1. **Hermes 词库（升级库、复习库、错误档案、笔记评论缓存）只存在 Rust 侧 SQLite，这是唯一事实源。** 前端不直接碰 SQL。
2. **访问层用现有 `rusqlite` + 自写 Tauri command**，不引入 Tauri 官方 SQL 插件（避免两套访问层混用；本地词典已经是这条路）。词库用**独立的数据库文件**，不和本地词典库混在一起。
3. **前端只通过一个 `vocabApi` 薄层调用 command**，组件里不出现 command 名字以外的存储细节，方便以后换成同步层。
4. **LinguaClip 现有 IndexedDB（精听卡片、FSRS、音频）不迁移。** 阶段 3「听错词入库」只加一个写入 Hermes「待考察」的入口并保存来源引用，不做 FSRS ↔ L1–L4 换算。
5. **每条记录必须有稳定 ID**（不能用单词文本当主键，因为复习库有 6 组重复词目），并保留原 Markdown 行号/原文，保证能无损导出回 Markdown。
6. 第 6 节的 7 张拆卡建议基本采纳，正式拆卡时由 Claude 写验收标准。
